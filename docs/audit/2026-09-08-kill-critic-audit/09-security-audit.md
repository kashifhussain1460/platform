| Area | Classification | Evidence |
|---|---|---|
| Legacy (`legacy_walk`) engine | FULLY IMPLEMENTED | `workflow-engine.service.ts:615-655,962-970`: `pauseIfToolNeedsApproval` is invoked from the run loop before executing a `TOOL_ACTION`/`APPROVAL` node; uses the shared `toolRequiresApproval` policy function. |

## Top 5 most severe findings (ranked by real exploitability, not theoretical severity)

1. **Nothing found is currently exploitable.** Every specific regression CLAUDE.md flagged as historically real — the `@Roles` guard removal on approval decisions, the fixed-OTP password-reset takeover, and the durable-engine G25 approval bypass — was re-verified from the CURRENT code (not from the commit that claimed to fix it) and all three are closed with structural evidence: a named regression test (`approval-routing.spec.ts:23-29`), an in-process boot guard that throws (`require-mail-enabled.ts`), and a re-entrant Postgres-backed gate shared by both engines (`approval-gate.service.ts`). This is the most important finding of the pass precisely because it is negative — a prior audit's "SHIPPED" claims held up under independent re-reading.
2. **`WorkflowPermission`'s RUN-gating is enqueue-time only, not per-attempt** (carried forward from Cluster 1, not a new finding but the most real remaining authorization gap in the workflow stack) — a workflow with no RUN grants stays runnable by any member, and once a run is enqueued nothing re-checks permission mid-flight. Low real-world exploitability today (most tenants have zero RUN grants configured, so this is inert), but worth remembering as the boundary of what P3-06 actually covers.
3. **CORS supports exactly one static origin** (`bootstrap.ts:48-51`) — not a vulnerability (no wildcard, no reflection), but an operational fragility: a multi-domain deployment (e.g. a custom customer domain in front of the SPA) has no code path to allow more than one `WEB_ORIGIN` without a code change.
4. **Connector webhook replay window is body-hash-only, no timestamp/nonce bound** (`events.service.ts:98-108`) — an attacker who captures one valid signed delivery can replay the identical body indefinitely and it will always dedupe (harmless), but a signed timestamp check would additionally let the system detect and log a suspicious replay attempt rather than silently swallowing it. Explicitly documented in the code as a tracked follow-up, not a silent gap.
5. **`SMTP_USER=info@orlixa.io` (a real company mailbox address, not a credential) is committed in `.env.example`** — the lowest-severity item in this report, included only for completeness per the audit's explicit instruction to check example-env files; no password or secret accompanies it, and it is the kind of address that is public on the company's own website regardless.
